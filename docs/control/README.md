# Control study

**Purpose:** before building anything that runs inside real programs, find out in simulation what pacing GPU work could buy (less temperature swing, less chip wear), what it costs (runtime, energy), and which way of pacing works.

**Status: simulation only.** The "GPU" being controlled is the [thermal model](../model/thermal-model.md), driven by the real rocHPL power trace. The controller is given numbers fitted on a different stretch of data, so it's slightly wrong, as in real life.

| Page | Answers |
|---|---|
| [Fatigue scoring](fatigue-scoring.md) | How "less wear" is measured |
| [Sleeps and power caps](sleeps-and-caps.md) | Pausing vs slowing down, and how long a pause can safely be |

**What came out of it:**
1. **Pauses must be short.** A pause longer than ~20–50 ms lets the die cool and reheat, so each pause becomes a temperature cycle of its own. Long pauses can wear the chip *more* than doing nothing.
2. **Slowing down (a power cap) is cheaper than pausing,** if lowering the clock saves power faster than it loses speed, which is typical but unmeasured here. For the same temperature: +9% runtime with a cap against +21% with pauses.
3. **A cap updated every 1–5 s, using a 5 s forecast, works about as well as one updated every millisecond.** So no millisecond control loop is needed.

These shaped the [runtime governor](../runtime/README.md): gaps of at most 5 ms, chosen from a forecast.
